# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

An Electron app that turns a PC visual novel (VN) into a portrait, phone-friendly view. It captures the game window, redraws it as a 9:16 layout (cropped background on top, enlarged text box below, big buttons), and that view is streamed to a phone with Apollo/Sunshine + Moonlight over Tailscale. Taps then get translated back into clicks or keys in the game. Target platform is Windows. The final streaming programs are flexible.

`portrait-layout.md` records the portrait's sizes and positions (background defaults, text sizing, message window, corner buttons, current game profiles, and where each is set in code). Keep it up to date when changing any of them; the user tunes the text box against it.

`getting-started.md` is the design and planning doc. It covers the four sub-problems (capture, reformat, stream, input), the chosen tools (desktopCapturer, OCR with tesseract.js first and Textractor later, koffi for `SendInput`/`PostMessage`, Apollo, Tailscale) and the milestone plan. Its **Status** section, at the top, says what's done, the key decisions, known gaps and the next step. Read it first in a new session, and check the plan before starting a milestone.

## About the user

They're returning to programming after ~7 years and are new to TypeScript. Explain unfamiliar patterns briefly, especially Electron's main/preload/renderer split and TypeScript-specific syntax. Prefer small, milestone-sized changes they can test and commit.

Their knowledge of web and tooling practices may be outdated, and they've asked for guidance. When they suggest a technique and a better current best practice exists, don't just build what they asked. Say so before building, explain why the alternative is better in plain terms, and urge them to consider it. They make the final call. (Example: they suggested flexbox for the portrait zones; CSS Grid named areas fit better.)

## Commands

- `npm start`: run the app in dev mode (Electron Forge + Vite, with hot reload for the renderer). Type `rs` in that terminal to restart after main-process or preload changes.
- `npm run start:debug`: the same, in debug mode (`--vn-debug`; not `--debug`, which Electron rejects as an old Node flag): every OCR read, its confidence and time, is printed in the terminal, and the picker shows its **Debug** tools (the OCR test button and its "Clean up image" checkbox, **Save as OCR test…** and **Show OCR tests**; `isDebug()`).
- While the user has `npm start` running, edits to renderer files (`capture.ts`, `text-reader.ts`, the pages) hot-reload into their open app, so mid-work they're seeing whichever version is on disk; main-process files (`ocr.ts`, `main.ts`, `preload.ts`) need a restart (`rs`, or stop and start again for `start:debug`). Tell them when an OCR change is being tried live. Their sightings are useful but can mislead: a running app may mix new renderer code with an old main process. A bigger re-read of failed reads looked like it fixed Aokana's "N..." live, but that app still ran an older `ocr.ts`; the real frame, saved as an OCR test after a restart, read right with or without it, so it was taken out. Confirm with a saved frame (and a restart) before keeping a change on what was seen live.
- `npm run ocr-bench`: runs the text reader on every saved **OCR test** and scores it (exact reads, letters wrong, text made up in empty boxes, lines missed). `npm run ocr-bench -- <commit> <commit>` also builds and runs those commits side by side; `--only <name>` filters tests, `--scales 1` runs full size only (default 100, 80 and 60%), `--verbose` prints every OCR attempt. Tests are saved from the picker in debug mode (**Save as OCR test…**: the game's client area as a PNG at capture size, the regions, and the correct text, prefilled with what the app shows; `src/ocr-tests.ts`) into `%APPDATA%\mobile-novel\ocr-tests\`, not the repo (it's public; the frames are game art). The bench (`tools/ocr-bench/`) bundles each version's `ocr.ts`, `capture.ts` and `text-reader.ts` with rolldown and runs them in a hidden Electron window the way the portrait does (each test at 100%, 80% and 60%). Run it before and after any OCR change, and add a test whenever the user reports a misread. A test can also hold a page of full-screen text (`page` region and `expectedPage`, paragraphs separated by a blank line; the dialog's **Full-screen text** box), scored with its paragraph breaks kept (as ¶); `katawa-shoujo-nvl-page` was made from a screenshot the user shared (its mouse pointer reads as a stray word: a known miss).
- `npm run typecheck`: `tsc --noEmit`
- `npm run lint`: oxlint plus an oxfmt format check. `npm run lint:fix` fixes both.
- `npm run package` / `npm run make`: build a distributable (Squirrel installer on Windows).

There's no test framework set up yet.

## Architecture

Electron Forge's Vite plugin (`forge.config.mts`) builds three separate bundles, each with its own Vite config:

- **Main process:** `src/main.ts` with `vite.main.config.mts`. Node/Electron APIs live here: window creation, `desktopCapturer`, and later the native input helper.
- **Preload:** `src/preload.ts` with `vite.preload.config.mts`. Output is `preload.cjs`, loaded by path in `main.ts`. This is the only bridge between main and renderer: expose APIs via `contextBridge`, then call into main via `ipcRenderer.invoke`/`ipcMain.handle`.
- **Renderer:** two pages built by `vite.renderer.config.mts` (multi-page `rolldownOptions.input`), each in its own window: `index.html` → `src/renderer.ts` (window picker; "Your games" and the window list are `<details>`, and the window list folds once a game is picked) + `src/region-editor.ts` (region outlines with move/resize handles and snapping) + `src/preview-zoom.ts` (zoom by laying `#zoom-box` out bigger inside the scrolling `#preview-area`, not a CSS transform, so the editor's `getBoundingClientRect` maths still holds) and `portrait.html` → `src/portrait.ts` (the streamed portrait view). Both run with Node integration disabled and share `src/preload.ts`. `desktopCapturer` is **not** available here; get source IDs from main over IPC, then capture with `playCapture()` from `src/capture.ts`.
- **Shared state lives in main** (the selected source ID and the `Regions`). Pages read it with a `get-*` invoke, change it with a `set-*`/`select-*` invoke, and main pushes changes to the portrait window with `webContents.send`. Shared types (`WindowSource`, `Region`, `Regions`, the `window.vn` API) are in `src/declarations.d.ts`.

Each entry in the `renderer` array of `forge.config.mts` (currently only `main_window`) generates build-time globals `<NAME>_VITE_DEV_SERVER_URL` and `<NAME>_VITE_NAME`. `main.ts` uses these (via its `loadPage` helper) to load a page from the dev server in dev, or the built file when packaged. A new window's page goes in as another HTML input in `vite.renderer.config.mts`, like `portrait.html`.

Packaged builds have Electron fuses set (`RunAsNode` off, `OnlyLoadAppFromAsar` on, asar integrity validation). Code shouldn't rely on loading files from outside the asar at runtime unless they're explicitly unpacked.

## Conventions

- Formatting is enforced by oxfmt: single quotes, 80-column width.
- Styling: **themes** in `src/theme.css` (`@import`ed by `index.css` and `portrait.css`), picked in the picker's **Style settings** (`#theme` select; an app setting, `theme` in `settings.json`, saved straight away and broadcast to both windows as `theme-changed`). `src/theme.ts` (imported by `renderer.ts` and `portrait.ts`) sets `data-theme` on `<html>` and loads every theme's bundled font (`@fontsource-variable/nunito`, `@fontsource-variable/eb-garamond`, `@fontsource/share-tech-mono`, `@fontsource-variable/jura`) so they work offline. Plain `:root` is the default, **Aokana** (bright sky blue and white); the others are `:root[data-theme='…']` blocks (each also matches `.theme-sample[data-theme='…']`, so the Menus sheet's theme buttons can each show their own theme): You and Me and Her (`kimikano`), Katawa Shoujo (`katawa-shoujo`), Witch on the Holy Night (`mahoyo`), Hoshizora no Memoria (`hoshimemo`), Steins;Gate (`steins-gate`), Doki Doki Literature Club! (`ddlc`), MiSide (`miside`; its glass has a doodle wallpaper of hearts, flowers, stars and rings in an even, tilted grid) and Miyuki's Realm (`miyuki`: a lavender-grey panel with a bevelled frame on every `.glass`, purple text in Jura). Some themes come with their own border or arrow, picked along with the theme by main, whichever window picks it (`THEME_STYLES` in `src/look-options.ts`, which also lists every theme, border and arrow with its name, for the picker's selects and the Menus sheet): You and Me and Her picks border None and the chevron (its message window is a white haze over the whole text zone, with no glass), MiSide the Hearts arrow, Miyuki's Realm border None and the Triangle; `ThemeName` in `declarations.d.ts`. A theme is a full set of variables: colours (`--accent`, `--accent-deep`, `--accent-pale`, `--ink`, `--line`, `--on-accent`, `--surface`, `--surface-tint`, `--shadow`, `--deep`, `--stage-top`, `--backdrop-tint`, `--rim-light`), and shape and type (`--glass-pattern`, `--glass-blur`, `--font`, `--text-weight`, `--corner`, `--pill`), each explained at the top of `theme.css`. Never hard-code a colour, font or radius in a style; use these variables, with `color-mix(in srgb, var(--accent) 35%, transparent)` for see-through shades (the region editor's overlay colours are the one exception: they stay the same in every theme). The portrait's message window is frosted glass (`backdrop-filter`). Its border effect and "next" arrow are picked in the picker's **Style settings** or the portrait's Menus sheet (`src/message-style.ts`; an app setting, `messageStyle` in `settings.json`, saved straight away; `MessageStyle` in `declarations.d.ts`): border Halo (default), Turning rim, Ribbon or None; arrow Chevron (default), Dots, Triangle, Hearts, Ember, Drop or None. portrait.ts sets them as `data-border` on `#text-line` and `data-arrow` on `#next-arrow` (and on `.portrait`, for `--arrow-width`), and `portrait.css` styles by those. The style rules match `:is(#text-line, .message-window)` and `:is(#next-arrow, .next-arrow)` (and `:is(#name-tag, .name-tag)`), so the Menus sheet's samples share them with the same specificity; theme overrides in `theme.css` use the same `:is()` forms. Both windows follow `message-style-changed`, which main sends to every window, the sender included. The arrow is `#next-arrow`, a sibling of `#text-line` (setting the line's text would wipe anything inside it) holding every arrow shape, of which CSS shows one. The text wraps around the arrow: `#text-line::after` reserves room at the end of the last line from the picked arrow's `--arrow-width` (set on `.portrait[data-arrow='…']`), so a new arrow must set its width there too. The picker's controls are plain selects for now; the user will restyle them later.
- **Every style option must exist in every theme.** When adding a new style option (a border, an arrow, a button look, a new element), build it only from the theme variables, then check it in every theme (light and dark ones differ the most). Where the shared version doesn't suit a theme, add that theme's own version under its `:root[data-theme='…']` block (a new variable, or an override rule), so no theme is left without it. When adding a new theme, define every variable `:root` defines, add it to `ThemeName` and the picker's `#theme` select, and check every existing style option in it.
- Each game has a **profile** (`GameProfile` in `src/declarations.d.ts`): one JSON file per game in `%APPDATA%\mobile-novel\games\` (`app.getPath('userData')`), handled by `src/profiles.ts`. It holds the exe path, title, click method, background height (`backgroundY`, where the background sits top to bottom; picker slider in `src/background-view.ts`), text style (`size`, a multiplier on the message window's font size, and `nameSize`, the name tag's size relative to the text, sent to the portrait as `--name-size`; picker sliders in `src/text-style.ts`), regions, client-area size and last-played time. Format `version: 3`. Settings made of several values (`regions`, `textStyle`) are laid over their defaults on load, so fields added later get defaults without a version bump. Older version-2 files (named after the window title) are upgraded in memory on pick, keeping their regions, and the old file is deleted on first save. Profiles are keyed by the lowercase `.exe` name (`exePathOf()` in `win32.ts`), falling back to `title:<window title>` if the exe can't be read. Main holds the picked game's `profile` and replaces it immutably on each change. **Saving is manual** (the user's choice): edits apply live, but nothing is written until the picker's Save button or Ctrl+S (`save-profile`). Unsaved edits are detected by comparing against `savedSnapshot`. Switching games or closing the picker with unsaved edits shows a Save / Don't save / Cancel dialog (`resolveUnsavedEdits`). Saves are announced with `profiles-changed`, and the button state with `save-state-changed`. Right-clicking a game card opens a native menu (`show-profile-menu`, built with `Menu.buildFromTemplate` in main) with Pick / Show file in folder / Delete (confirmed with a dialog). Not-running cards use `aria-disabled`, not `disabled`, so they still receive right-clicks. The picker's "Your games" list comes from `list-profiles`, which marks each profile open/closed by matching the exes of open windows. Regions are fractions (0 to 1) of the game's **client area** (the window minus title bar, borders and menu bar), never of the whole capture and never screen pixels. Renderers convert using the client area from `window.vn.getClientArea()`. Currently `background`, `text`, `name` (the name box: who's speaking) and `page` (where full-screen text goes; defaults to the whole game less a 1–2% margin, since text touching the crop's edge is cleared; picker button **Edit full-screen text**, its outline shown only while it's edited and left out of snapping); button regions are deferred. The portrait runs a second `startTextReader` on the name box (with `retryFlattened`: a read that comes back as garbage is retried with `cropForOcr(…, 'flatten')`, which removes the background by subtracting a blurred copy; Aokana's white name on a light gradient plate reads at ~20% normally and 96% flattened, while flattening makes ordinary text worse; flattened reads need `MIN_FLATTENED_CONFIDENCE` (80), since flattening turns edges in the art into stroke-like marks: a hair outline read as "7 WN" at 55) (`setSpeaker` → main keeps the latest read as `nameRead` and the shown `speaker`, broadcasting `speaker-changed`, cleared like the line. Every change of name, appearing, going or switching, only shows when the text line changes, so the name always belongs to the line on screen; a name read within `SPEAKER_CATCH_UP` (2s) of a line change belongs to that line) and shows it in `#name-tag` on the message window's top-left corner: an accent pill overlapping the window's top edge (hidden while empty, i.e. narration; You and Me and Her shows plain text, Miyuki's Realm the bevelled frame).
- Layouts follow responsive design: CSS Grid with named areas for page/zone layout, flexbox only for one-dimensional rows, `fr`/`clamp()` instead of fixed pixel sizes, and media/container queries for big shape changes. Don't hard-code an output resolution; the portrait view must fit whatever size the window or streamed display is.
- Each canvas is resized by a `ResizeObserver` to its box size × `devicePixelRatio`. Crops are placed by `placeInZone()` (`src/zone-view.ts`, shared by the portrait and the picker) from a `ZoneView`: `fill` blends from show-all (0) to fill/cover (1), `x`/`y` line the picture up (which part shows when trimmed, where it sits when there's space around it). Both zones share one grid cell: the background fills the portrait and the text panel (a gradient scrim) lies over its bottom, so the text never moves the background. The background picture never moves because of the text (the user treats that as a bug): it's placed in the full canvas and the window always lies over it. The window's text size is `--chosen-font-size` (= `--base-font-size`, the 100% size defined once at the top of `portrait.css`, × `--text-size`), and its height (a 3-line `min-height`) is worked out from it. The background uses `BACKGROUND_VIEW` (`src/zone-view.ts`): zoom 20% and centered left to right, fixed for every game on purpose; its `y` (20% down) is only the default for the game's own `backgroundY` (the picker's **Portrait height** slider). Older profiles' saved `backgroundView` is dropped on load. The picker's "Portrait view" box (`src/background-view.ts`) outlines the visible part using the zone size the portrait reports via `setBackgroundZoneSize`. Space around a zoomed-out background is filled with a blurred, darkened copy (drawn tiny and stretched, for speed; shrunk with `imageSmoothingQuality = 'high'` and blended over the last few frames, `BACKDROP_BLEND`, so tiny changes in the capture don't make it shimmer).
- Capture targets a specific app window (`desktopCapturer` window source), not a screen area. On Windows its source ID (`window:<HWND>:0`) carries the HWND (verified), which `src/win32.ts` uses for Win32 calls.
- Taps in the portrait are mapped back through each zone's scaling (`placeZone()` in `portrait.ts`, shared with drawing) to a point in the game's client area, then clicked by main via `postClick` (posted messages) or `sendClick` (`SendInput`) in `src/win32.ts`. The portrait window is `focusable: false` so it never takes focus from the game; this also means keyboard shortcuts (e.g. Ctrl+Shift+I) don't reach it. On Windows that also hides it from the taskbar and Alt+Tab, so `main.ts` adds `WS_EX_APPWINDOW` (`showInTaskbar()` in `win32.ts`) and calls `setSkipTaskbar(false)` to put it back. Its title bar wouldn't work while non-focusable (Chromium answers `WM_MOUSEACTIVATE` with "no activation, discard the click"), so `hookWindowMessage(WM_MOUSEACTIVATE)` makes it focusable (and focuses it) when the click's hit-test isn't `HTCLIENT` (title bar, borders), before Chromium answers (verified with a probe: page clicks don't activate, title clicks do and drag). Hooking `WM_NCLBUTTONDOWN` doesn't work: that message never arrives. and the `blur` handler makes it non-focusable again (and re-applies the taskbar fix, which `setFocusable` resets).
- **Streaming (Milestone 4):** Apollo on the PC, Artemis on the user's Android phone. Apollo adds a virtual display the phone's size while streaming and streams only that. `src/phone-display.ts` (main) moves the portrait onto it and makes it full screen, and puts it back on the PC when it's removed (watches `screen` display events, debounced). The display is recognized by its adapter name (`/SudoMaker|SudoVDA/i`, via `displayAdapterAt()` in `win32.ts`: `MonitorFromPoint` → `GetMonitorInfoW` → `EnumDisplayDevicesW`), never by shape (the user's HP 727pq monitor is portrait) or label (Apollo names it after the client). Main broadcasts `phone-display-changed`; the picker shows a status pill (`src/phone-status.ts`) and the portrait gets an `on-phone` class (hides the mouse pointer). Leaving Artemis without quitting only _pauses_ the session, and Apollo keeps the display while paused, so the portrait would stay out of sight on it: the picker's PC / Phone switch (`#portrait-place`, radio buttons styled as one pill by the `.switch` class; `set-portrait-on-phone` → `setOnPhone`) moves it between the two while the display exists (`PhoneDisplay.portraitOnPhone`). Back on the PC, the portrait keeps its left edge and shape but takes the picker's top edge and height (`toHeightOf`, with the picker passed in as `heightGuide`); `setBounds` is called twice there, because crossing from the phone's display (100% scaling) to the PC monitor (150%) rescales the window after the first call. The switch is always shown and is saved straight away as an **app setting** (`src/settings.ts`: `settings.json` in `userData`, laid over defaults on load, no Save button; `get-`/`set-portrait-on-phone`), so it stays on PC even when the phone connects. The picker's **Button size** slider (`src/button-size.ts`, `buttonSize`, sent to the portrait as `--button-size`) is another app setting; main saves it once the slider stops moving (debounced). Corner buttons are sized in `vmin` with no `rem` cap, because the phone's display is far more CSS pixels wide than the PC window (100% vs 150% scaling). The portrait window has Windows' `EdgeGesture_DisableTouchWhenFullscreen` property set (`blockEdgeSwipesWhenFullScreen()` in `win32.ts`, a COM property-store call through koffi), because swiping up to leave Artemis also reaches the PC as a touch swipe from the bottom edge, which would raise the taskbar. Not a duplicate view on purpose: that would need a second portrait window, with a second capture and a second OCR reader.
- Minimized windows can't be captured or clicked (Windows doesn't draw them; engines pause). Main polls the selected game once a second and calls `restoreBehind()` (`win32.ts`: un-minimize without activating, then `HWND_BOTTOM`) if it's minimized. `click-game` does the same before clicking. The picker's "Send game to back" button is the supported way to hide the game. The same 1-second check notices when the game's window is gone (`windowExists()`): main forgets `selectedSource` (the profile and unsaved edits stay), clears the text line and broadcasts `source-selected` with `null`; the portrait clears its canvases and shows a message, the picker stops its preview and unfolds the window list. Separately, main lists window IDs (no thumbnails, cheap) every 2 seconds and broadcasts `windows-changed` when the set changes; the picker then refreshes its window list and game cards (it also refreshes when it gets focus).
- Win32 calls go through koffi (v3: pointers are BigInts, so HWNDs are declared as `intptr_t` and passed as numbers) in `src/win32.ts`, main process only. koffi is marked external in `vite.main.config.mts` because native modules can't be bundled.
- OCR runs in main (`src/ocr.ts`, tesseract.js in a worker thread, also marked external). Renderers crop the text region to a PNG (`regionInVideo()` + `cropForOcr()` in `capture.ts`) and send it with `window.vn.readText`. Each crop is enlarged to suit its text (`ocrScale()`: the median height of the runs of rows with writing, scaled toward `TARGET_LETTER_HEIGHT`, 55 px, which beat 40–70 in a bench of past misreads, 1–4×, 2× when nothing is measured). (A guess that letters under 14 px were a pixel font, enlarged with hard edges, was removed: it misfired on small smooth text, Aokana's "N..." read as "NM...". Pixel-font handling waits for a pixel-font game in the OCR tests.) The `'clean'` prep then makes it black text on white (`toBlackOnWhite()`: text is whichever way stands out from the median, light or dark; pixels past halfway to the text's brightness are ink, which also drops art seen through a see-through box like Katawa Shoujo's; marks touching the crop's edge, the box's frame or cut-off art, are cleared, so a region needs a little room around its text). `readText` (`ocr.ts`) then judges each word, not the whole line: words the wrong height for the line (under `MIN_WORD_HEIGHT` or over `MAX_WORD_HEIGHT` times the median height of its words at least `SURE_WORD` sure; punctuation-only words only checked for being too tall; a too-tall word Tesseract is sure of is kept, since blobs of art read at 0–34% while a real word with the mouse pointer touching it stays sure) are dropped as junk (frame slivers, blobs of art), and so is a line of its own made only of unsure words under `MAX_MARK_HEIGHT` (the box's ▼ arrow read as "wv", the pointer) or lying entirely in the right `ARROW_ZONE` (20%) of the crop, where the "next" arrow sits (a real line, even a wrapped word, starts at the left), and the read's confidence is re-averaged from the words kept; if more than `MAX_DROPPED_SHARE` of the letters were dropped, the real text was misread too, so the read keeps Tesseract's original, lower score. Height, not confidence, is the test, since real words can score low (Katawa Shoujo's "Hi..." read right at 20%). Dropped words are logged in debug mode. `fixCommonMistakes` turns a word of only 7s and ?s into ?s (Katawa Shoujo's "???" reads as "777"). Tesseract runs in single-block page mode (`PSM.SINGLE_BLOCK`) with a fixed DPI, set once in `getWorker()`. The picker's debug OCR test shows the scale and letter height. The portrait runs the automatic reader (`src/text-reader.ts`) and sends each confirmed line to main (`setTextLine`). The text box's reader has `textBox`, which also looks at the box's picture (`measureInk()`, at full size, measured against the box height): a read under `MIN_CONFIDENCE` but at least 35% is kept when the box is light with a text-like amount of ink (`hasWriting()`; short lines like "...I see." read at ~51%, while junk from bare art fails the ink check), and a box of only a few small, separate dark marks (`readDots()`, flood fill) reads as that many dots, one "…" per three, since Tesseract reads a line of only "..." as nothing at all. Words may start with trailing-off dots ("...I") in `WORD`. Main keeps the current line and broadcasts `text-line-changed`, so text sources stay swappable. Main also keeps the **history log**: the last 30 non-empty lines, each with its speaker (`HistoryEntry`, `getTextHistory`; a speaker confirmed within `SPEAKER_CATCH_UP` of a line is taken as that line's, since the two boxes are read separately), cleared when another game is picked. The portrait's Log button (top-right) opens it as a native `<dialog>` (`showModal()`, `src/history-log.ts`): a snapshot shown one line at a time, newest first, with big ◀ / ▶ buttons and "Return to game". The frosted look is a shared `.glass` class in `portrait.css`; the corner pills share `.corner-button`. The top-left **Menus** button is raw mode (3c): a `raw-mode` class on `.portrait` gives the background zone the whole portrait and hides the text zone, and `zoneRegion()`/`zoneView()` in `portrait.ts` make the background zone show the full client area with `SHOW_ALL`, so taps map 1:1 through the same `placeZone()`. It's session-only (not saved). In it the portrait's grid becomes `buttons` / `game` / `sheet` (side by side in landscape): the background canvas still fills the portrait (blurred backdrop), but the game is drawn into the box of `#game-slot` (`slotInCanvas()`; its height from `--game-aspect`, set from the capture, at most 55dvh), and below it the **Menus sheet** (`#menus-sheet`, `src/menus-sheet.ts`) picks the look with big buttons: themes drawn in their own theme, moving arrows, small message windows with each border, and a sample message window in the current look. At the sheet's top is the **Full-screen text** switch (Off / On; `src/page-mode.ts`, session-only like Menus, since games switch between full-screen text and a text box): the `page-mode` class shows `#page-view` (glass with the message window's border, holding the scrolling `#page-text`) in place of the line and name, growing up to the background picture's bottom edge (`--picture-bottom`, reported by portrait.ts from `placeZone()` each frame outside Menus mode), but always allowed 45dvh and never past the corner buttons, then scrolling (by finger, `touch-action: pan-y`, or by mouse drag in page-view.ts, since phone taps may arrive as mouse input; a drag's click is cancelled so it doesn't advance the game; the top edge fades once scrolled, and the arrow hides while scrolled back from the end); the text and name readers rest (`active` option of `startTextReader`) and a third reader reads the `page` region with `page: true`, which keeps the paragraphs `readText` returns (`paragraphs`: lines split where the gap is over `PARAGRAPH_GAP`, 0.4, of the usual line height; in Katawa Shoujo 0.22 inside a paragraph, 0.68 between) joined by a blank line. `src/page-view.ts` compares each confirmed page with the last (`whatsNew`: paragraphs at least `SAME_PARAGRAPH`, 85%, alike by edit distance count as the same, so a re-read with a letter wrong adds nothing; a grown last paragraph adds only the added part; anything else is a new page), sends each new paragraph to main with `setTextLine` (so the history log gets it once), dims the ones already read (`.read`) and scrolls to the new text (to its start if it doesn't fit). Taps on the page click the page region's bottom-right corner (`PAGE_CORNER`), where the mouse pointer (the capture shows it) stays off the text. Turning it on clears the speaker. Auto-detecting full-screen text is for later, once the bench has frames for it. The English data is downloaded on first use into `userData/tessdata`. **Known gap:** Forge's Vite plugin packages only `.vite/`, so `npm run package` won't include koffi or tesseract.js yet; it needs copying in (e.g. a `packageAfterCopy` hook) and unpacking from the asar before packaged builds work.
