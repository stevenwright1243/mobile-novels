# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

An Electron app that turns a PC visual novel (VN) into a portrait, phone-friendly view. It captures the game window, redraws it as a 9:16 layout (cropped background on top, enlarged text box below, big buttons), and that view is streamed to a phone with Apollo/Sunshine + Moonlight over Tailscale. Taps then get translated back into clicks or keys in the game. Target platform is Windows. The final streaming programs are flexible.

`portrait-layout.md` records the portrait's sizes and positions (background defaults, text sizing, message window, corner buttons, current game profiles, and where each is set in code). Keep it up to date when changing any of them; the user tunes the text box against it.

`getting-started.md` is the design and planning doc. It covers the four sub-problems (capture, reformat, stream, input), the chosen tools (desktopCapturer, OCR (now OneOCR, the Snipping Tool's engine) and the game's memory, koffi for `SendInput`/`PostMessage`, Apollo, Tailscale) and the milestone plan. Its **Status** section, at the top, says what's done, the key decisions, known gaps and the next step. Read it first in a new session, and check the plan before starting a milestone.

## About the user

They're returning to programming after ~7 years and are new to TypeScript. Explain unfamiliar patterns briefly, especially Electron's main/preload/renderer split and TypeScript-specific syntax. Prefer small, milestone-sized changes they can test and commit.

Their knowledge of web and tooling practices may be outdated, and they've asked for guidance. When they suggest a technique and a better current best practice exists, don't just build what they asked. Say so before building, explain why the alternative is better in plain terms, and urge them to consider it. They make the final call. (Example: they suggested flexbox for the portrait zones; CSS Grid named areas fit better.)

## Commands

- `npm start`: run the app in dev mode (Electron Forge + Vite, with hot reload for the renderer). Type `rs` in that terminal to restart after main-process or preload changes.
- `npm run start:debug`: the same, in debug mode (`--vn-debug`; not `--debug`, which Electron rejects as an old Node flag): every OCR read, its confidence and time, is printed in the terminal, and the picker shows its **Debug** tools (the OCR test button, **Save as OCR test…**, **Show OCR tests**, and a **Log OCR reads** checkbox that quiets the per-read lines until the next start; `isDebug()`). The portrait's Menus sheet then has a **Debug** drop-down too, last (`<details id="debug">`, `src/debug-panel.ts`), so it can be done from the phone: **Save as OCR test** in one tap (the portrait can't be typed in, being `focusable: false`, so the test is saved with what the app showed as its expected text and `unchecked: true`; fill in the right text from the frame, by looking at the PNG, then take `unchecked` out; the bench skips and lists unchecked tests), **Read the text box now** (one read, its image and result) and the Log OCR reads switch. Both windows' tools share `src/ocr-debug.ts` (`readTextBoxOnce`, `grabClientArea`).
- While the user has `npm start` running, edits to renderer files (`capture.ts`, `text-reader.ts`, the pages) hot-reload into their open app, so mid-work they're seeing whichever version is on disk; main-process files (`ocr.ts`, `main.ts`, `preload.ts`) need a restart (`rs`, or stop and start again for `start:debug`). Tell them when an OCR change is being tried live. Their sightings are useful but can mislead: a running app may mix new renderer code with an old main process. A bigger re-read of failed reads looked like it fixed Aokana's "N..." live, but that app still ran an older `ocr.ts`; the real frame, saved as an OCR test after a restart, read right with or without it, so it was taken out. Confirm with a saved frame (and a restart) before keeping a change on what was seen live.
- `npm run ocr-bench`: runs the text reader on every saved **OCR test** and scores it (exact reads, letters wrong, text made up in empty boxes, lines missed). `npm run ocr-bench -- <commit> <commit>` also builds and runs those commits side by side; `--only <name>` filters tests, `--scales 1` runs full size only (default 100, 80 and 60%), `--verbose` prints every OCR attempt. Tests are saved from the picker in debug mode (**Save as OCR test…**: the game's client area as a PNG at capture size, the regions, and the correct text, prefilled with what the app shows; `src/ocr-tests.ts`) into `%APPDATA%\mobile-novel\ocr-tests\`, not the repo (it's public; the frames are game art). The bench (`tools/ocr-bench/`) bundles each version's `ocr.ts`, `oneocr.ts`, `win32.ts`, `capture.ts` and `text-reader.ts` with rolldown (versions from before OneOCR need tesseract.js, which is no longer installed, so they can't be compared) and runs them in a hidden Electron window the way the portrait does (each test at 100%, 80% and 60%). Run it before and after any OCR change, and add a test whenever the user reports a misread. The project skill `ocr-tests` (`.claude/skills/ocr-tests/SKILL.md`) walks through checking tests the user saved: filling in what each frame shows, finding the cause, and fixing it with the bench before and after. A test can also hold a page of full-screen text (`page` region and `expectedPage`, paragraphs separated by a blank line; the dialog's **Full-screen text** box), scored with its paragraph breaks kept (as ¶); `katawa-shoujo-nvl-page` was made from a screenshot the user shared (its mouse pointer reads as a stray word: a known miss).
- `npm run typecheck`: `tsc --noEmit`
- `npm run lint`: oxlint plus an oxfmt format check. `npm run lint:fix` fixes both.
- `npm run package` / `npm run make`: build a distributable (Squirrel installer on Windows).

There's no test framework set up yet.

## Architecture

Electron Forge's Vite plugin (`forge.config.mts`) builds three separate bundles, each with its own Vite config:

- **Main process:** `src/main.ts` with `vite.main.config.mts`. Node/Electron APIs live here: window creation, `desktopCapturer`, and later the native input helper.
- **Preload:** `src/preload.ts` with `vite.preload.config.mts`. Output is `preload.cjs`, loaded by path in `main.ts`. This is the only bridge between main and renderer: expose APIs via `contextBridge`, then call into main via `ipcRenderer.invoke`/`ipcMain.handle`.
- **Renderer:** two pages built by `vite.renderer.config.mts` (multi-page `rolldownOptions.input`), each in its own window: `index.html` → `src/renderer.ts` (the picker: a sidebar with "Your games", rows showing the game's .exe icon (`icon` in `ProfileSummary`, a `data:` URL from `app.getFileIcon`, cached per .exe in main; its first letter if none; faded while not running) that a click picks if running or starts if not, with a ✕ that force-closes a running one and "Open · muted" on running games not being played, the "Open windows" `<details>`, which folds once a game is picked, and the phone status and PC / Phone switch at the bottom; on the right a top bar with the game's title, Short name box and Save, and tabs for the pages Regions (the region editor and preview), Style (the Menus sheet's Sizes panel, `src/picker-sizes.ts` drawing its sample from the preview at the portrait's size, and under it the Look card: theme, border and arrow selects), Input (the Menus sheet's Input Settings panel, with its own Save / Reset) and Debug (debug mode only). No zoom pad, q.Save / q.Load buttons or Log, which are the portrait's) + `src/region-editor.ts` (region outlines with move/resize handles and snapping) + `src/preview-zoom.ts` (zoom by laying `#zoom-box` out bigger inside the scrolling `#preview-area`, not a CSS transform, so the editor's `getBoundingClientRect` maths still holds) and `portrait.html` → `src/portrait.ts` (the streamed portrait view). Both run with Node integration disabled and share `src/preload.ts`. `desktopCapturer` is **not** available here; get source IDs from main over IPC, then capture with `playCapture()` from `src/capture.ts`.
- **Shared state lives in main** (the selected source ID and the `Regions`). Pages read it with a `get-*` invoke, change it with a `set-*`/`select-*` invoke, and main pushes changes to the portrait window with `webContents.send`. Shared types (`WindowSource`, `Region`, `Regions`, the `window.vn` API) are in `src/declarations.d.ts`.

Each entry in the `renderer` array of `forge.config.mts` (currently only `main_window`) generates build-time globals `<NAME>_VITE_DEV_SERVER_URL` and `<NAME>_VITE_NAME`. `main.ts` uses these (via its `loadPage` helper) to load a page from the dev server in dev, or the built file when packaged. A new window's page goes in as another HTML input in `vite.renderer.config.mts`, like `portrait.html`.

Packaged builds have Electron fuses set (`RunAsNode` off, `OnlyLoadAppFromAsar` on, asar integrity validation). Code shouldn't rely on loading files from outside the asar at runtime unless they're explicitly unpacked.

## Conventions

- Formatting is enforced by oxfmt: single quotes, 80-column width.
- Styling: **themes** in `src/theme.css` (`@import`ed by `index.css` and `portrait.css`, as are `src/reader.css`, the reader screen's layout, message window, name tag, borders, arrows and corner buttons, in container units (`cqw`/`cqh`/`cqmin` of the nearest `.portrait` or `.sample-screen`, `container-type: size`) so the picker's copy of the screen lays out as the portrait does, and `src/settings-panel.css`, the shared Sizes and Input Settings panels' sliders, switches, chips and Save / Reset / Default), picked with the picker's **Theme** button at the bottom of its sidebar, above the phone status (`#theme-button`, opening the `#theme-menu` popover of theme buttons, each drawn in its own theme, `src/theme-picker.ts`, placed with CSS anchor positioning), the Style page's `#theme` select, or the Menus sheet's Themes (an app setting, `theme` in `settings.json`, saved straight away and broadcast to both windows as `theme-changed`). `src/theme.ts` (imported by `renderer.ts` and `portrait.ts`) sets `data-theme` on `<html>` and loads every theme's bundled font (`@fontsource-variable/nunito`, `@fontsource-variable/eb-garamond`, `@fontsource/share-tech-mono`, `@fontsource-variable/jura`) so they work offline. Plain `:root` is the default, **Aokana** (bright sky blue and white); the others are `:root[data-theme='…']` blocks (each also matches `.theme-sample[data-theme='…']`, so the Menus sheet's theme buttons can each show their own theme): You and Me and Her (`kimikano`), Katawa Shoujo (`katawa-shoujo`), Witch on the Holy Night (`mahoyo`), Hoshizora no Memoria (`hoshimemo`), Steins;Gate (`steins-gate`), Doki Doki Literature Club! (`ddlc`), MiSide (`miside`; its glass has a doodle wallpaper of hearts, flowers, stars and rings in an even, tilted grid) and Miyuki's Realm (`miyuki`: a lavender-grey panel with a bevelled frame on every `.glass`, purple text in Jura). Some themes come with their own border or arrow, picked along with the theme by main, whichever window picks it (`THEME_STYLES` in `src/look-options.ts`, which also lists every theme, border and arrow with its name, for the picker's selects and the Menus sheet): You and Me and Her picks border None and the chevron (its message window is a white haze over the whole text zone, with no glass), MiSide the Hearts arrow, Miyuki's Realm border None and the Triangle; `ThemeName` in `declarations.d.ts`. A theme is a full set of variables: colours (`--accent`, `--accent-deep`, `--accent-pale`, `--ink`, `--line`, `--on-accent`, `--surface`, `--surface-tint`, `--shadow`, `--deep`, `--stage-top`, `--backdrop-tint`, `--rim-light`), and shape and type (`--glass-pattern`, `--glass-blur`, `--font`, `--text-weight`, `--corner`, `--pill`), each explained at the top of `theme.css`. Never hard-code a colour, font or radius in a style; use these variables, with `color-mix(in srgb, var(--accent) 35%, transparent)` for see-through shades (the region editor's overlay colours are the one exception: they stay the same in every theme). The portrait's message window is frosted glass (`backdrop-filter`). Its border effect and "next" arrow are picked in the picker's **Style settings** or the portrait's Menus sheet (`src/message-style.ts`; an app setting, `messageStyle` in `settings.json`, saved straight away; `MessageStyle` in `declarations.d.ts`): border Halo (default), Turning rim, Ribbon or None; arrow Chevron (default), Dots, Triangle, Hearts, Ember, Drop or None. portrait.ts sets them as `data-border` on `#text-line` and `data-arrow` on `#next-arrow` (and on `.portrait`, for `--arrow-width`), and `portrait.css` styles by those. The style rules match `:is(#text-line, .message-window)` and `:is(#next-arrow, .next-arrow)` (and `:is(#name-tag, .name-tag)`), so the Menus sheet's samples share them with the same specificity; theme overrides in `theme.css` use the same `:is()` forms. Both windows follow `message-style-changed`, which main sends to every window, the sender included. The arrow is `#next-arrow`, a sibling of `#text-line` (setting the line's text would wipe anything inside it) holding every arrow shape, of which CSS shows one. The text wraps around the arrow: `#text-line::after` reserves room at the end of the last line from the picked arrow's `--arrow-width` (set on `.portrait[data-arrow='…']`), so a new arrow must set its width there too. The picker's controls are plain selects for now; the user will restyle them later.
- **Every style option must exist in every theme.** When adding a new style option (a border, an arrow, a button look, a new element), build it only from the theme variables, then check it in every theme (light and dark ones differ the most). Where the shared version doesn't suit a theme, add that theme's own version under its `:root[data-theme='…']` block (a new variable, or an override rule), so no theme is left without it. When adding a new theme, define every variable `:root` defines, add it to `ThemeName` and the picker's `#theme` select, and check every existing style option in it. Some options look different on light and dark glass: the Hearts arrow is an accent fill with a deep-accent outline by default (a pale glow blurs into light glass), while dark themes get MiSide's pale glow from one rule in `theme.css` listing them. When adding a theme or changing one's `--surface` between light and dark, add it to or take it out of that list.
- Each game has a **profile** (`GameProfile` in `src/declarations.d.ts`): one JSON file per game in `%APPDATA%\mobile-novel\games\` (`app.getPath('userData')`), handled by `src/profiles.ts`. It holds the exe path, title, an optional short `name` (shown instead of the title in the Menus sheet's Visual Novels; the picker's **Short name** box in its top bar, `#game-name`, `set-game-name`/`game-name-changed`, an unsaved edit like the rest, empty for none; `snapshot` keeps it as `null` when unset, since JSON drops `undefined`), click method, background height (`backgroundY`, where the background sits top to bottom; the Sizes slider; the picker's Portrait view box in `src/background-view.ts`), text style (`size`, a multiplier on the message window's font size, and `nameSize`, the name tag's size relative to the text, sent to the portrait as `--name-size`; Sizes sliders), regions, client-area size and last-played time. Format `version: 3`. Settings made of several values (`regions`, `textStyle`) are laid over their defaults on load, so fields added later get defaults without a version bump. Older version-2 files (named after the window title) are upgraded in memory on pick, keeping their regions, and the old file is deleted on first save. Profiles are keyed by the lowercase `.exe` name (`exePathOf()` in `win32.ts`), falling back to `title:<window title>` if the exe can't be read. Main holds the picked game's `profile` and replaces it immutably on each change. **Saving is manual** (the user's choice): edits apply live, but nothing is written until the picker's Save button or Ctrl+S (`save-profile`). Unsaved edits are detected by comparing against `savedSnapshot`. Switching games or closing the picker with unsaved edits shows a Save / Don't save / Cancel dialog (`resolveUnsavedEdits`). Saves are announced with `profiles-changed`, and the button state with `save-state-changed`. Right-clicking a game row opens a native menu (`show-profile-menu`, built with `Menu.buildFromTemplate` in main) with Pick / Show file in folder / Delete (confirmed with a dialog). Rows that can't be started (no .exe saved) use `aria-disabled`, not `disabled`, so they still receive right-clicks. The picker's "Your games" list comes from `list-profiles`, which marks each profile open/closed by matching the exes of open windows. Regions are fractions (0 to 1) of the game's **client area** (the window minus title bar, borders and menu bar), never of the whole capture and never screen pixels. Renderers convert using the client area from `window.vn.getClientArea()`. Currently `background`, `text`, `name` (the name box: who's speaking) and `page` (where full-screen text goes; defaults to the whole game less a 1–2% margin, since text touching the crop's edge is cleared; picker button **Edit full-screen text**, its outline shown only while it's edited and left out of snapping); button regions are deferred. Beside the regions, the profile has **spots** (`points`: `Points`, a `GamePoint` or null per `PointName`, fractions of the client area like regions, laid over `DEFAULT_POINTS` on load, `get-points` / `set-point` / `points-changed`, part of the unsaved edits): `quickSave` and `quickLoad`, the game's own quick save and quick load buttons, placed in the picker with **Place q.Save** / **Place q.Load** (region-editor.ts's `placing`, beside `editing`: click or drag in the preview puts the spot there, the edit panel shows only X and Y via its `placing` class hiding `.box-only`, arrow keys nudge; each shows as a `.marker`, a ring with its name, hidden until placed) and tapped with `clickGame` by the zoom pad's **q.Save** / **q.Load** (`src/quick-save.ts`; disabled until placed or with no game picked). The portrait runs a second `startTextReader` on the name box (with `retryFlattened`: a read that comes back as garbage is retried with `cropForOcr(…, 'flatten')`, which removes the background by subtracting a blurred copy; Aokana's white name on a light gradient plate reads at ~20% normally and 96% flattened, while flattening makes ordinary text worse; flattened reads need `MIN_FLATTENED_CONFIDENCE` (80), since flattening turns edges in the art into stroke-like marks: a hair outline read as "7 WN" at 55) (`setSpeaker` → main keeps the latest read as `nameRead` and the shown `speaker`, broadcasting `speaker-changed`, cleared like the line. Every change of name, appearing, going or switching, only shows when the text line changes, so the name always belongs to the line on screen; a name read within `SPEAKER_CATCH_UP` (2s) of a line change belongs to that line) and shows it in `#name-tag` on the message window's top-left corner: an accent pill overlapping the window's top edge (hidden while empty, i.e. narration; You and Me and Her shows plain text, Miyuki's Realm the bevelled frame).
- Layouts follow responsive design: CSS Grid with named areas for page/zone layout, flexbox only for one-dimensional rows, `fr`/`clamp()` instead of fixed pixel sizes, and media/container queries for big shape changes. Don't hard-code an output resolution; the portrait view must fit whatever size the window or streamed display is.
- Each canvas is resized by a `ResizeObserver` to its box size × `devicePixelRatio`. Crops are placed by `placeInZone()` (`src/zone-view.ts`, shared by the portrait and the picker) from a `ZoneView`: `fill` blends from show-all (0) to fill/cover (1), `x`/`y` line the picture up (which part shows when trimmed, where it sits when there's space around it). Both zones share one grid cell: the background fills the portrait and the text panel (a gradient scrim) lies over its bottom, so the text never moves the background. The background picture never moves because of the text (the user treats that as a bug): it's placed in the full canvas and the window always lies over it. The window's text size is `--chosen-font-size` (= `--base-font-size`, the 100% size defined once at the top of `portrait.css`, × `--text-size`), and its height (a 3-line `min-height`, `--three-lines`, registered with `@property` as a length so it reads back in pixels; in Text position Top the window fits its text instead, never squeezed below 3 lines or its text: `calc-size(max-content, clamp(<1 line>, size, var(--three-lines)))`, at least 1 line so an empty window isn't a thin strip) is worked out from it. The background uses `BACKGROUND_VIEW` (`src/zone-view.ts`): centered left to right; its `width` (75%) and `y` (20% down) are only the defaults for the game's own `backgroundWidth` (how much of the background's width shows, 50–100%; the **Portrait width** sliders) and `backgroundY` (the **Portrait height** sliders). `ZoneView.width` zooms by that share (`placeInZone()`), so a given % looks the same in every game; other views zoom by `fill`. (The zoom used to be fixed for every game, showing 74–79% of the width; the user chose a per-game slider.) Older profiles' saved `backgroundView` is dropped on load. The picker's "Portrait view" box (`src/background-view.ts`) outlines the visible part using the zone size the portrait reports via `setBackgroundZoneSize`. Space around a zoomed-out background is filled with a blurred, darkened copy (drawn tiny and stretched, for speed; shrunk with `imageSmoothingQuality = 'high'` and blended over the last few frames, `BACKDROP_BLEND`, so tiny changes in the capture don't make it shimmer).
- Capture targets a specific app window (`desktopCapturer` window source), not a screen area. On Windows its source ID (`window:<HWND>:0`) carries the HWND (verified), which `src/win32.ts` uses for Win32 calls.
- Taps in the portrait are mapped back through each zone's scaling (`placeZone()` in `portrait.ts`, shared with drawing) to a point in the game's client area, then clicked by main via `postClick` (posted messages) or `sendClick` (`SendInput`) in `src/win32.ts`. Unity games (Aokana) take posted clicks only while they're focused **and** the real cursor is over them (tested: either missing, the click is ignored), so taps from the phone, which park the cursor on the phone's display, need the Mouse method there. The portrait window is `focusable: false` so it never takes focus from the game; this also means keyboard shortcuts (e.g. Ctrl+Shift+I) don't reach it. On Windows that also hides it from the taskbar and Alt+Tab, so `main.ts` adds `WS_EX_APPWINDOW` (`showInTaskbar()` in `win32.ts`) and calls `setSkipTaskbar(false)` to put it back. Its title bar wouldn't work while non-focusable (Chromium answers `WM_MOUSEACTIVATE` with "no activation, discard the click"), so `hookWindowMessage(WM_MOUSEACTIVATE)` makes it focusable (and focuses it) when the click's hit-test isn't `HTCLIENT` (title bar, borders), before Chromium answers (verified with a probe: page clicks don't activate, title clicks do and drag). Hooking `WM_NCLBUTTONDOWN` doesn't work: that message never arrives. and the `blur` handler makes it non-focusable again (and re-applies the taskbar fix, which `setFocusable` resets).
- **Streaming (Milestone 4):** Apollo on the PC, Artemis on the user's Android phone. Apollo adds a virtual display the phone's size while streaming and streams only that. `src/phone-display.ts` (main) moves the portrait onto it and makes it full screen, and puts it back on the PC when it's removed (watches `screen` display events, debounced). The display is recognized by its adapter name (`/SudoMaker|SudoVDA/i`, via `displayAdapterAt()` in `win32.ts`: `MonitorFromPoint` → `GetMonitorInfoW` → `EnumDisplayDevicesW`), never by shape (the user's HP 727pq monitor is portrait) or label (Apollo names it after the client). Main broadcasts `phone-display-changed`; the picker shows a status pill (`src/phone-status.ts`) and the portrait gets an `on-phone` class (hides the mouse pointer, since taps arrive as mouse input and would show it jumping; a mouse paired with the phone shows it while moving: `pointer-shown`, set in portrait.ts after `MOVES_TO_SHOW` (3) moves in a row with no button held, removed after `HIDE_AFTER` (2 s) still). Leaving Artemis without quitting only _pauses_ the session, and Apollo keeps the display while paused, so the portrait would stay out of sight on it: the picker's PC / Phone switch (`#portrait-place`, radio buttons styled as one pill by the `.switch` class; `set-portrait-on-phone` → `setOnPhone`) moves it between the two while the display exists (`PhoneDisplay.portraitOnPhone`). Back on the PC, the portrait keeps its left edge and shape but takes the picker's top edge and height (`toHeightOf`, with the picker passed in as `heightGuide`); `setBounds` is called twice there, because crossing from the phone's display (100% scaling) to the PC monitor (150%) rescales the window after the first call. The switch is always shown and is saved straight away as an **app setting** (`src/settings.ts`: `settings.json` in `userData`, laid over defaults on load, no Save button; `get-`/`set-portrait-on-phone`), so it stays on PC even when the phone connects. The **Button size** slider (Sizes, `buttonSize`, sent to the portrait as `--button-size`) is another app setting; it's saved with the Save button, like the game's settings (see the Menus sheet's Sizes). Corner buttons are sized in `vmin` with no `rem` cap, because the phone's display is far more CSS pixels wide than the PC window (100% vs 150% scaling). The portrait window has Windows' `EdgeGesture_DisableTouchWhenFullscreen` property set (`blockEdgeSwipesWhenFullScreen()` in `win32.ts`, a COM property-store call through koffi), because swiping up to leave Artemis also reaches the PC as a touch swipe from the bottom edge, which would raise the taskbar. Not a duplicate view on purpose: that would need a second portrait window, with a second capture and a second OCR reader.
- Minimized windows can't be captured or clicked (Windows doesn't draw them; engines pause). Main polls the selected game once a second and calls `restoreBehind()` (`win32.ts`: un-minimize without activating, then `HWND_BOTTOM`) if it's minimized. `click-game` does the same before clicking. The Input page's (and the Menus sheet's Input Settings') "Send game to back" button is the supported way to hide the game. The same 1-second check notices when the game's window is gone (`windowExists()`): main forgets `selectedSource` (the profile and unsaved edits stay), clears the text line and broadcasts `source-selected` with `null`; the portrait clears its canvases and shows a message, the picker stops its preview and unfolds the window list. Separately, main lists window IDs (no thumbnails, cheap) every 2 seconds and broadcasts `windows-changed` when the set changes; the picker then refreshes its window list and game cards (it also refreshes when it gets focus).
- **Muting and the default pick:** every 2 seconds (and on each pick or close) main's `muteOtherGames()` mutes every saved game but the picked one and unmutes the picked one (`setMutes()` in `win32.ts`: Windows' Core Audio sessions through koffi COM calls, on every playback device, matched by the session's process `.exe` against saved profile IDs; other programs are left alone; with no game window picked, nothing is muted). Muting is re-applied, so a game's sound only needs to appear in the Volume mixer once. On `will-quit` every game is unmuted (a killed app, e.g. Ctrl+C on `npm start`, can leave one muted until the app runs again). While no game is picked (at startup, or after the picked game closes) and no launch is pending, the windows check picks the open saved game whose process started last (`mostRecentlyOpenedGame`, `startTimeOf()` via `GetProcessTimes`), unless a closed game's profile has unsaved edits (picking would ask about them out of the blue).
- Win32 calls go through koffi (v3: pointers are BigInts, so HWNDs are declared as `intptr_t` and passed as numbers) in `src/win32.ts`, main process only. koffi is marked external in `vite.main.config.mts` because native modules can't be bundled.
- OCR runs in main with **OneOCR**, the OCR engine inside Windows 11's Snipping Tool (`src/oneocr.ts`: `oneocr.dll` through koffi, `recognize()` returning lines of words with boxes and 0–100 confidences; undocumented, its functions and model key from the `oneocr` Python package, github.com/AuroraWright/oneocr). Windows won't load a DLL from a Store app's folder into another program (access denied), so on first use its three files (`oneocr.dll`, `oneocr.onemodel`, `onnxruntime.dll`, ~115 MB) are copied from the Snipping Tool's folder (`packageFolder()` in `win32.ts`, by package family, no PowerShell) into `userData/oneocr`, again when the Snipping Tool's version folder changes (`from.txt`), and loaded with `loadLibraryNextTo()` (`LoadLibraryExW` with `LOAD_WITH_ALTERED_SEARCH_PATH`, so its `onnxruntime.dll` is the one beside it, not Windows' own). Reads run on koffi's thread (`.async`). If it can't load, every read fails and main shows the reason once in a message box (`read-text`); there's no fallback engine (the user's choice; docTR via ONNX Runtime was the runner-up). It replaced tesseract.js in Oct 2026 after a shootout of 28 engine setups on the OCR tests (branch `ocr-shootout`, `tools/ocr-shootout/RESULTS.md`): in the app's bench 0.3% of letters wrong against Tesseract's 6.2%, no line missed against 24, in half the time; vision-language models (Qwen3-VL, GLM-OCR, PaddleOCR-VL…) read as well but are 10–30× slower and make up text for empty boxes. Renderers crop the box to a PNG as it is (`regionInVideo()` + `cropBox()` in `capture.ts`, high-quality smoothing since region edges fall between pixels) and send it with `window.vn.readText`; no enlarging or black-on-white preparation: that was Tesseract's, and it broke OneOCR's reads of outlined text (7.9% wrong). OneOCR reads bare art as nothing (all 42 empty-box reads), so the many junk filters Tesseract needed (word height, the arrow's corner, wide gaps, the 'white' and 'flatten' second reads, digits read as letters) were taken out after none fired once in a bench run; see git history before Oct 31 2026 if a new engine ever needs them. `readText` (`ocr.ts`) keeps only what fires with OneOCR: `joinMarks` joins a word of only dots, or a quote mark ending a line, to the word before it, and one starting a line to the word after ("Ah ..." → "Ah...", "... I see" → "...I see"); `withoutDoubles` keeps only the longer of two lines overlapping by over `MAX_LINE_OVERLAP` (text at the box's top edge read twice, "Most" over "Most people? Who's most people?"); `withoutLoneEnd` drops a lone letter (or `|`) with no punctuation right after a word ending a sentence, at the very end of the read and of each paragraph, never mid-text, where it's a sentence wrapping to the next line ("I tried to read them. I"; drawn tests `synthetic-lone-letter-*`, two with the junk and two that must stay as they are: a wrapped "…them. I / wanted to…" and "plan B"), likewise a word of only dashes, commas, tildes and the like, but not one of only `.`, `!`, `?`, `…`, quotes and brackets; `fixCommonMistakes` turns `|` and a lone "l" into "I" ("I-l did it") and ".." into "..." ("N.."); paragraphs split where the gap is over `PARAGRAPH_GAP` (0.3) of the usual line height. The read's confidence is its words' average. Dropped words are logged in debug mode. The portrait runs the automatic reader (`src/text-reader.ts`) and sends each confirmed line to main (`setTextLine`). A read counts as text when it's at least `MIN_CONFIDENCE` (40) sure and mostly words (`looksLikeText`; real lines read at 88–99%, but quote marks and dots pull short ones down: "...I see." at 59%, a lone "“" at 8%). The text box's reader (`textBox`) also looks at the box's picture (`measureInk()`, at full size): a box of only a few small, separate dark marks reads as that many dots, one "…" per three, when OCR reads nothing (`readDots()`, flood fill via `markSizes()`; made for Tesseract, which never read "..."); `hasWriting()` (a light box with a text-like amount of ink or a mark bigger than a dot) is Auto's `boxHasWriting`. Words may start with trailing-off dots ("...I") in `WORD`. Main keeps the current line and broadcasts `text-line-changed`, so text sources stay swappable. **Exact text from memory** (`src/memory-text.ts`, per game, `textFromMemory` in the profile, on for new games; the switch and its status in Input Settings, `set-text-from-memory` / `memory-text-status-changed`): games keep the line they show in memory, at addresses that change each run. **Finding it:** when OCR confirms a line, main searches the game's writable private memory (read-only: `openForReading`, `writableRegions`, `readMemoryAsync` in `win32.ts`, 0.3–1 s, in the background) for up to `NEEDLES` (8) runs of its plain-letter words (OCR may have garbled any of them; `MIN_NEEDLE` 12 letters, or `MIN_SHORT_NEEDLE` 8 when nothing that long is left) as UTF-16 and UTF-8, noting what each copy holds; when a later line comes, every copy that has **changed** to it (`MATCH`, 60% alike by letters) is followed (only changed ones: OCR reads the same line a little differently each time, and the game's script, which never changes, matches every read of it; a read `SAME_LINE`-alike to the last one searched for isn't searched again). **Until then, each line is matched on its own** (status `matching`, "Found: each line OCR reads is corrected from the game"): every search also takes the copy that best matches OCR's read (`bestCopy`: formatting codes stripped by `clean`, Unity's `<alpha=#f8>` typewriter redraws and Ren'Py's `{w}`, plus undecodable and invisible characters; the line's start looked for around where a run of its words puts it, since a copy can have other text before it, like Aokana's script with every language's version in a row) and sends it as a correction (`onMemoryCorrection` → main replaces the shown line, and its history entry, if OCR's read is still shown); a re-read of a corrected line keeps it (`corrected`). The quote marks at its ends follow OCR's read (`withQuotes`: Ren'Py draws a character's quotes around text stored without them, and a copy can carry a stray one). Each search runs whatever the last search's copies did (in engines that never rewrite a buffer, none ever changes). **A followed copy has to keep proving itself:** it's only taken up if it holds all of OCR's read (`holdsWhole`: no letters from another writing system, within 5% of its length, the first 10 letters 80% alike), and when OCR later reads clearly more of a line than the copies hold, starting the same way (`isPartOf`; Ren'Py's typewriter effect builds the line a letter at a time as new strings that can reuse the same memory, so Katawa Shoujo once locked onto "I ponder … snowfall graduall" for "As I ponder … thickens."), OCR's read shows, and `MAX_WRONG_FOLLOWS` (2) in a row stop following for the run (`noFollowing`), back to matching line by line. Characters from a writing system the read doesn't use, or half a UTF-16 pair, are trimmed off the match's ends (Ren'Py's object header read as text, "踁This is…"), and don't count as a word the line starts inside of. This is how engines that never rewrite a buffer get exact text: Unity and Ren'Py make a new string for every line. **Following a pointer to the line** ("Following a pointer to the line" in memory-text.ts): those engines still keep a pointer to the string on screen, set to each new line's string. After each line matched one by one (`lookForPointers`, from the search, `nextInScript` and `catchUp`), `findPointers` finds the strings of just that line (`letters` equal; `textStart` skips a string's length read as its first character, "%I almost…") and every pointer to them (any value from the text back to `MAX_HEADER`, 64 bytes, in 4-byte steps, so the string's header is learned: Mono's 12 bytes in 32-bit, 20 in 64-bit; the pointer's size from `pointerSizeOf()` in win32.ts, `IsWow64Process`), as `pointerCandidates`: `Spot`s with `pointer: { size, offset }`, read through by `textAt` (`pointedTo`). `followChangedCopies` checks them with the copies; one that moved on to the next line, its string just the line (nothing after it, so the script's entry with every language isn't followed), is followed as the buffer (its new string all new, not `newLine`, and never `showWhole`), so memory leads. `MAX_POINTER_SEARCHES` (5) looks that find none stop it for the run; following resets the count. Text is read through codecs (`src/text-codec.ts`: `UTF16`, `UTF8`, and `AlphabetCodec` for a learned `Alphabet`, saved per game in `settings.json`'s `alphabets` by profile ID, straight away, via `onAlphabetLearned` → main; `startReading` gets it back). After `EMPTY_SEARCHES_TO_LEARN` (2) searches with no copy, `learnAlphabet` does a **relative search** (`relativeSearch`): a long lowercase word from OCR's read, looked for as its pattern of steps between codes (fonts keep letters in order), in 2-byte big- and little-endian and 1-byte codes; a find counts if most of the line's lowercase letters fit around it (`fitLine`, `MIN_FIT`), and the line then teaches the codes of characters next to ones already known (`learnFromLine`, passes repeating, so it spreads from letters to spaces to a lone "I"). Later lines matched in the alphabet with codes not yet known teach those too (`refineAlphabet`, then decoded again: "can't", "?"). Steins;Gate: learned in 0.6–0.8 s. A saved alphabet is searched from the first line (`alphabetFound` starts true, reset if it finds nothing before it has found text this run: `alphabetAssumed`). The alphabet's decoding skips **markup** inside a line (`markupEnd` in text-codec.ts: a run of `MIN_MARKUP` (2) to `MAX_MARKUP` non-text codes, at least one not zero (a lone code ends the line, so one ending in a letter or comma isn't joined to the next), after a letter, digit, space or comma and before a known character; Steins;Gate colours a word with 0x0482 0x0000 … 0x0480 0x0000), and finds a string's ends past it (`stringStart`, `stringEnd`). **Following the script:** where lines are matched one by one, main keeps where the last one is (`lastLine`, set from the match's copy), and `lineForRead` first checks that string (only when `SAME_LINE`-alike: more of the same line read; a new line can be much like the last) and the `NEXT_LINES` (4) after it (`nextInScript`, one 4 KB read) before any search (but after checking whether the last search's copies changed to the line, `followChangedCopies`, so a line buffer is still found and followed): instant, and in a game's own alphabet (strings ended by a code, 0x03ff) it also takes a line OCR read only the start of (`isNextLine` with `startOnly`: "“What!?" when the rest is in red OCR can't read, or a line still being typed), its unknown codes learned from that start (`learnFromLine`, lined up with the string's own codes, markup left out and nothing past its end: `textCodes`, also used by `refineAlphabet`) and a closing quote mark from its last code (`learnClosingQuote`, only right after `.`, `!`, `?` or `…`, since a code learned wrong stays wrong), its end kept as memory has it (`withQuotes` with `atEnd` false). In UTF-16/UTF-8 a string can run on into an older one's leftovers ("rude?#8c> handmade soba…" in Aokana), so there the line is cut by `endFor` and must match all of the read. Where only lines are matched, a search across all of memory tries the first `FIRST_NEEDLES` (2) runs first, then the rest if they find nothing. A line OCR reads while a search runs waits (`waiting`) and is looked up when it ends (`catchUp`: the next in the script, or searched), so it isn't skipped. Lines never start with `NOT_A_START` marks (the end of a name stored before the line, "【Girl】：" in Aokana, or The Colorful World's "`"). Work still under way for a game no longer read (another picked, or switched off) stops before reading memory or reporting anything (`stale`: the closed handle may be given to the next game). **Then memory leads:** main checks the copies every `POLL_EVERY` (150 ms) and shows each new line as soon as the copies agree on it (`onMemoryLine`→`showLine`in main), even when OCR can't read it at all (The Colorful World's "No, I haven't.", "......"). A new line overwrites the start of the last one, so the line ends where the two texts stop agreeing, counted back from the end, then on to the next end mark (`newLine`); the end mark is the mark after the first line (The Colorful World's `~`), or learned later; inside a line the same mark is the game's own line break ("I think I~finally") and becomes a space. To guarantee those 3 lines, **Portrait height is capped** in Top: `updateBackgroundYCap()`in portrait.ts works out each frame, from the picture's height on screen and the room the zone needs at 3 lines (gap, padding, name tag less its overlap, the window at 3 lines, `--three-lines`; measured from those parts on the reader's zone, or the Sizes sample's in Menus mode, not from the zone's own height, which is squeezed when the picture is too low), the highest `backgroundY`that leaves that room, into`backgroundYCap`(portrait-sizes.ts; not a setting, not sent to main). The background is drawn at`min(backgroundY, cap)`, and the Menus slider shows and stops at the cap; a higher value set in the picker is kept but held at the cap. Bottom has no cap. (Before: a 60dvh cap, then a cap at the screen's bottom with no scrolling.), so it grows downward, and keeps the name tag's room while there's no name (`visibility: hidden`instead of`display: none`), so a name coming or going never moves the window's top edge. The text zone is `position: relative`, so the arrow is placed in the window's corner wherever the zone sits (it used to measure from the screen's bottom, which only matched for Bottom). In Menus mode `drawSample()`reports`--picture-bottom`for the reader (the reader's own drawing doesn't then). Beside the sliders while it's open,`#sizes-sample`shows a live miniature of the reader screen:`.sample-screen`is the reader's layout at full size (100vw × 100dvh, so every`vw`/`vmin`/`dvh`size in it is the real one) holding a canvas, the corner buttons and a`.text-zone`with the current line and name (stand-ins when there are none), shrunk with`scale`to the height of the slider column beside it (their own height,`slidersHeight()`; the column spreads its rows over that height, so the Text position row lines up with the sample's bottom; at most 50% of the drop-down's width, `MAX_SAMPLE_SHARE`, and slider names don't wrap, so the two can't feed each other) (`fitSample()`in portrait.ts); portrait.ts draws the picture into it each frame at the game's`backgroundY`. The reader's rules in portrait.css (and the You and Me and Her haze in theme.css) match `:is(#text-zone, .text-zone)`, `:is(#text-line, .text-zone .message-window)`, `:is(#name-tag, .text-zone .name-tag)`and`:is(#next-arrow, .text-zone .next-arrow)`, with the same specificity as the IDs alone, so the miniature gets the same styles. Opening the drop-down scrolls the sheet to it. Under Sizes, a **Visual Novels** drop-down (`<details id="visual-novels">`, `src/visual-novels.ts`, sharing Sizes' summary styles) lists the saved profiles (`list-profiles`) as chips; tapping a running one calls `selectSource`, like a picker card (with the same unsaved-edits dialog), and the one being played is marked `aria-checked`. Tapping one that isn't running starts it (`launch-game`: a Steam game through Steam, `steam://rungameid/<id>`, its app ID found by `steamAppIdOf()`in`src/steam.ts`from the library's`appmanifest*\*.acf`, since started from its .exe it restarts itself through Steam and Aokana's second copy then failed with "already running"; any other a `spawn`of the saved`exePath`, detached, in the exe's own folder), and main picks it (`selectGame`, the `select-source` handler's body) once the 2-second windows check sees its window (`pendingLaunch`, for a minute; picked again if that window closes while another of the game's opens, e.g. a splash screen). A centered **Close** button at the bottom (`#close-game`, labelled with the game's title) force-closes the game played before the current one (the user's choice, for switching between two games): of the other running games, the one picked last (`pickedAt`, set in `selectGame`), or if none was picked, the one first seen open last (`openedAt`, a map main keeps from that same windows check; games already open when the app starts count as opened then), both sent in `ProfileSummary`; with no other game running, the current one with `taskkill /PID … /T /F` (`close-game`, `processIdOf()`in`win32.ts`), with no confirmation. Under it, an **Input Settings** drop-down (`<details id="input-settings">`, `src/input-settings.ts`, which fills the empty `.input-body` of either page, like Sizes) holds the click method as a Messages / Mouse switch (`#click-method`, the same `.toggle-switch`as Text position;`set-click-method`now broadcasts`click-method-changed` to every window, the sender included), an unsaved profile edit with its own Save and Reset (`.save-button`/`.reset-button`, wired with Sizes' in menus-sheet.ts), and under them **Bring game to front** (`bring-game-to-front`→`bringToFront()`in`win32.ts`: restores it if minimized, then `SetForegroundWindow`) and **Send game to back** (`send-game-to-back`), disabled with no game picked. Main broadcasts `source-selected`to both windows, and the picker shows a pick from either in its`onSourceSelected` handler (`showPicked`), not in `pickWindow`.
