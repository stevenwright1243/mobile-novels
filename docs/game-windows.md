# Clicking, focus and the game's window

How taps reach the game, keeping the portrait from taking focus, minimized and closed game windows, and muting other games (`src/win32.ts`, `src/main.ts`).

## Taps and focus

Taps in the portrait are mapped back through each zone's scaling (`placeZone()` in `portrait.ts`, shared with drawing) to a point in the game's client area, then clicked by main via `postClick` (posted messages) or `sendClick` (`SendInput`) in `src/win32.ts`. Unity games (Aokana) take posted clicks only while they're focused **and** the real cursor is over them (tested: either missing, the click is ignored), so taps from the phone, which park the cursor on the phone's display, need the Mouse method there. The portrait window is `focusable: false` so it never takes focus from the game; this also means keyboard shortcuts (e.g. Ctrl+Shift+I) don't reach it. On Windows that also hides it from the taskbar and Alt+Tab, so `main.ts` adds `WS_EX_APPWINDOW` (`showInTaskbar()` in `win32.ts`) and calls `setSkipTaskbar(false)` to put it back. Its title bar wouldn't work while non-focusable (Chromium answers `WM_MOUSEACTIVATE` with "no activation, discard the click"), so `hookWindowMessage(WM_MOUSEACTIVATE)` makes it focusable (and focuses it) when the click's hit-test isn't `HTCLIENT` (title bar, borders), before Chromium answers (verified with a probe: page clicks don't activate, title clicks do and drag), and the `blur` handler makes it non-focusable again (and re-applies the taskbar fix, which `setFocusable` resets). Hooking `WM_NCLBUTTONDOWN` doesn't work: that message never arrives.

## Minimized and closed windows

Minimized windows can't be captured or clicked (Windows doesn't draw them; engines pause). Main polls the selected game once a second and calls `restoreBehind()` (`win32.ts`: un-minimize without activating, then `HWND_BOTTOM`) if it's minimized. `click-game` does the same before clicking. The Input page's (and the Menus sheet's Input Settings') "Send game to back" button is the supported way to hide the game. The same 1-second check notices when the game's window is gone (`windowExists()`): main forgets `selectedSource` (the profile and unsaved edits stay), clears the text line and broadcasts `source-selected` with `null`; the portrait clears its canvases and shows a message, the picker stops its preview and unfolds the window list. Separately, main lists window IDs (no thumbnails, cheap) every 2 seconds and broadcasts `windows-changed` when the set changes; the picker then refreshes its window list and game cards (it also refreshes when it gets focus).

## Muting and the default pick

every 2 seconds (and on each pick or close) main's `muteOtherGames()` mutes every saved game but the picked one and unmutes the picked one (`setMutes()` in `win32.ts`: Windows' Core Audio sessions through koffi COM calls, on every playback device, matched by the session's process `.exe` against saved profile IDs; other programs are left alone; with no game window picked, nothing is muted). Muting is re-applied, so a game's sound only needs to appear in the Volume mixer once. On `will-quit` every game is unmuted (a killed app, e.g. Ctrl+C on `npm start`, can leave one muted until the app runs again). While no game is picked (at startup, or after the picked game closes) and no launch is pending, the windows check picks the open saved game whose process started last (`mostRecentlyOpenedGame`, `startTimeOf()` via `GetProcessTimes`), unless a closed game's profile has unsaved edits (picking would ask about them out of the blue).
